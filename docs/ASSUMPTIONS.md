# Допущения итерации 0.2

Реальные интервью с приёмщиком, диагностом и руководителем площадки в рамках текущей разработки недоступны. Ниже зафиксирован предполагаемый рабочий процесс, который необходимо проверить на пилотном автосалоне до production.

На момент старта 0.2 проверенная 0.1 ещё не была merged в `master`: её draft PR оставался открыт. Ветка 0.2 построена от проверенной integration head 0.1 (`13efe512e35b48de213a5f3fdceaba70bc7ed8a2`), которая имеет в ancestry и `master`, и проверенный product SHA `5323b0fccd86fa215835dab6c9a3257d9070e2e5`. Мердж 0.1 в `master` без подтверждения владельца не выполнялся.

## Рабочий процесс

1. После приёма на склад автомобиль находится в `InStock` и виден диагностам разрешённого филиала в очереди.
2. Команда начала осмотра атомарно создаёт `Inspection` и переводит его в `InProgress`; отдельный пользовательский шаг для пустого `Draft` не нужен.
3. Одновременно у автомобиля может быть только один `Draft` или `InProgress` inspection. Правило защищается сервером и partial unique index PostgreSQL.
4. Диагност фиксирует результат каждого пункта как `Pending`, `Pass`, `Fail` или `NotApplicable`. Обязательный пункт нельзя оставить `Pending` при завершении.
5. `Fail` не создаёт дефект автоматически: диагност описывает отдельный defect, чтобы не смешивать наблюдение и решение о подготовке.
6. `Critical` всегда включает `RepairRequired` и `BlocksSale` на сервере независимо от клиентского payload.
7. После завершения автомобиль получает `ReconditioningRequired`, если есть обязательный ремонт или блокировка продажи; иначе — `InspectionPassed`. `InspectionPassed` означает только технически пройденный осмотр. Полный `ReadyForSale` зарезервирован за будущим процессом после подготовки и контроля качества. При отмене активного осмотра автомобиль возвращается в `InStock`.
8. Завершённый результат, snapshot шаблона, дефекты и фотографии неизменяемы. Исправление оформляется новым inspection revision с явной ссылкой на исходный результат и отдельным audit trail, а не редактированием строк.
9. Черновик `ReconditioningPlan` относится к итерации 0.3. В 0.2 система только показывает следующее действие и обязательные дефекты, из которых такой черновик будет создан.

## Шаблоны

- Шаблон принадлежит организации и действует во всех её филиалах.
- Новая версия — новая неизменяемая запись; существующая версия не редактируется.
- При старте inspection пункты копируются в snapshot. Последующее создание версии шаблона не меняет старый inspection.
- Для demo seed используется один активный шаблон из 11 обязательных категорий.

## Фотографии

- Максимальный размер входного файла — 8 MiB.
- Разрешены JPEG, PNG и WebP.
- Расширение и `Content-Type` клиента не считаются доказательством формата: изображение декодируется и нормализуется сервером.
- Максимум 25 мегапикселей; metadata удаляется при повторном кодировании.
- Bucket закрытый. Клиент получает файл только через авторизованный API endpoint; presigned/public URL не выдаётся.
- Object key генерируется сервером и включает tenant, inspection, defect, photo и уникальный upload-attempt IDs.
- Метаданные БД создаются только после успешной загрузки. При ошибке сохранения БД загруженный object удаляется компенсирующей операцией.
- Повторный `photoId` идемпотентен только для того же inspection/defect; повторное назначение другому дефекту возвращает conflict.
- Correction создаёт новую photo metadata с `SourcePhotoId` и переиспользует неизменяемый object. Бинарный файл не копируется, а физическое удаление выполняется только после исчезновения последней metadata-ссылки.
- Удаление дефекта и tenant-aware запись отложенного удаления сохраняются одной DB-транзакцией. Недоступность MinIO логируется, оставляет запись для reconciliation и не возвращает пользователю ложный rollback.

## Проверить на интервью

- какие пункты могут быть `NotApplicable` и кто утверждает исключение;
- нужны ли нормативные значения измерений и единицы для отдельных категорий;
- кто имеет право отменять осмотр и создавать correction revision;
- допустимо ли завершение без фотографии Critical-дефекта;
- максимальные размеры/количество фотографий и политика хранения оригиналов;
- точное правило, когда Minor/Major defect становится обязательным ремонтом;
- какие подготовительные операции и второй контроль/подпись руководителя обязательны для будущего перехода в `ReadyForSale`.
